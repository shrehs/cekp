## P2.1: Fix Symbol Navigation (`__init__`, Method Lookup)

### The Problem

Current query:
```
"Find the __init__ method of Neo4jGraphRepository."
```

**What happens:**
1. Classifier tries to route to graph
2. Graph access denied by policy (v1 limitation)
3. Falls back to vector search
4. Query treats `__init__` as a global symbol search
5. Results are noisy (many `__init__` methods from other classes)

**What should happen:**
```
Query → Entity extraction: (class="Neo4jGraphRepository", symbol="__init__")
       → Intent: "method_in_class"
       → Graph operation: graph.get_methods_of_class("Neo4jGraphRepository")
       → Results: Only methods defined in that class
```

### Root Cause

The graph layer needs to understand **relationships between entities**, not just treat everything as global symbols.

Current limitation:
```python
# Current: treats each symbol independently
query_patterns = {
    "get_module_imports": r"what does .* import",
    "get_functions_in_module": r"functions in .*",
    # ... etc, no context about class vs method
}
```

What's needed:
```python
# Better: extract entities and relationships
class GraphQuery:
    def __init__(self, operation, target_class=None, target_method=None, ...):
        pass
    
    # Understands: "Find __init__ of Neo4jGraphRepository"
    # Extracts: (class="Neo4jGraphRepository", method="__init__")
    # Emits: graph.get_method_of_class(class, method)
```

### High-Value Fixes (in order)

1. **Class → Method navigation**
   - Pattern: `"<method> of <class>"`
   - Query: `graph.get_method_of_class(class_name, method_name)`
   - Expected impact: Fixes symbol-nav test, improves precision

2. **Class/Function location in file**
   - Pattern: `"<entity> in <file>"`
   - Query: `graph.get_functions_in_file(file) + graph.get_classes_in_file(file)`
   - Expected impact: Unblocks Q2 from benchmark (classes in planner.py)

3. **Import analysis (with context)**
   - Pattern: `"what does <module> import"`
   - Query: `graph.get_module_imports(module_name)`
   - Expected impact: Better dependency tracing

## P2.2: Natural-Language Graph Coverage Redesign

### Current Architecture (Fragile)

```
User question
    ↓
50 regex patterns (increasingly fragile)
    ↓
If match: graph query
If no match: vector search fallback
```

**Problem:** Each new query type requires new regex. Coverage plateaus quickly.

### Proposed Architecture (Scalable)

```
User question
    ↓
Intent Classifier (learned: "method_lookup", "import_analysis", etc.)
    ↓
Entity Extractor (extract: class, method, module, file names)
    ↓
Graph Operation Builder (build: graph.get_method_of_class(...))
    ↓
Graph Query Execution
    ↓
Result formatting
```

### Implementation Plan (Not yet executed)

**Phase 1: Intent expansion**
- Add new intent types: `method_lookup`, `class_definition`, `file_contents`, `import_analysis`
- Keep existing high-confidence patterns as "pattern-based intents" (fast path)
- Add fallback to learned intents (slower, more flexible)

**Phase 2: Entity extraction**
- Extract class names, method names, file paths, module names from query
- Use NER or simple pattern matching with context
- Examples:
  ```
  "Find __init__ of Neo4jGraphRepository"  → {entity_type: "method", entity: "__init__", in_class: "Neo4jGraphRepository"}
  "Classes in planner.py"                  → {entity_type: "classes", entity: "planner.py"}
  "What does app.core import"              → {entity_type: "imports", entity: "app.core"}
  ```

**Phase 3: Operation builder**
- Map (intent, entities) → graph operation
- Reusable patterns:
  ```python
  operations = {
      ("method_lookup", {"in_class": X}): lambda e: graph.get_method_of_class(e["in_class"], e["entity"]),
      ("class_definition", {"in_file": X}): lambda e: graph.get_classes_in_file(e["in_file"]),
      ("imports", {"module": X}): lambda e: graph.get_module_imports(e["module"]),
  }
  ```

## P2.3: Keep the Evaluator Honest

### The Crucial Distinction

Your P0 fix added `final_documents_count`. This revealed a critical distinction:

```
confidence = 0.85, documents = 0  →  MISLEADING (confidence without evidence)
confidence = 0.85, documents = 5  →  TRUSTWORTHY (confidence backed by evidence)
```

### The Original Bug

The old evaluator would return:
```json
{
  "confidence": 0.7,
  "documents": 0,
  "planner_outcome": "success"
}
```

This was nonsensical: the system claimed success but had zero evidence.

### What Changed

Now the evaluator correctly computes:
```python
planner_outcome = "success" if (any strategy cleared threshold AND has documents)
                  "no_evidence" if (all strategies failed or sub-threshold)
                  "error" if (exception occurred)
```

### What to Preserve & Extend

**Keep:**
- ✅ `final_documents_count` (always report actual count)
- ✅ `final_confidence` (only meaningful when documents > 0)
- ✅ `planner_outcome` computation (based on real evidence)

**Document (new in P2):**
- Distinguish in responses and logging:
  - **Retrieval Success:** "We found documents using strategy X"
  - **Evidence-backed Answer:** "Retrieval succeeded AND confidence > threshold"
  - **Answerability:** "Outcome is 'success' only if both above are true"

**Example response structure:**
```json
{
  "planner_outcome": "success",  // ← Only if evidence-backed
  "final_strategy_used": "hybrid",
  "final_confidence": 0.68,
  "final_documents_count": 5,    // ← CRUCIAL: Always report this
  "retrieval_succeeded": true,   // ← New: Was any strategy successful?
  "evidence_backed": true,       // ← New: Does confidence have documents?
  "attempts": [...]
}
```

### Why This Matters

It prevents the original bug: **false confidence without evidence**. Every confidence score must have a `documents_count` to back it up. If `documents_count = 0`, then `confidence` is meaningless, and `planner_outcome` should be `no_evidence`.
